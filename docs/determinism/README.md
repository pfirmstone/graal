# Native Image Reproducibility — program operating manual

This directory is a **machine-readable, self-propagating implementation plan** for
making GraalVM Native Image byte-reproducible. It is designed to be driven by AI
agents under an orchestrator.

## Why this exists

A determinism investigation (see the LLVM-backend work: commits `197c7aa`…`e426a92`,
`2f752a4`, and `substratevm/docs/llvm-backend-determinism-classifier-spec.md`) fixed
every nondeterminism source the LLVM backend controls (the parallel bitcode-id race
and statepoint/patchpoint id assignment) and **proved the residual is upstream and
backend-agnostic**: the points-to analysis produces a slightly different reachable
method/type/field set on each build (~45 methods observed), which renumbers type ids
and shifts field offsets throughout the image. The ordinary (non-LLVM) backend was
shown to diverge identically.

That single root cause is too large to attack head-on, so this plan decomposes it into
a task DAG across six stages (S0–S5), bisected by **stage checkpoint/replay** so each
pipeline stage can be tested for determinism in isolation.

## The artefacts

| Path | What it is |
|---|---|
| `tasks.yaml` | The master task DAG (all stages + review gates). Single source of truth. Validated by `schema/tasks.schema.json`. |
| `ORCHESTRATION.md` | The dispatch → complete → review → revise → emit-next-prompts loop. |
| `prompts/stage-N/*.md` | Ready-to-dispatch, cold-start agent prompts for stage N. **Only stage 0 is written up front**; later stages are generated by review gates. |
| `prompts/stage-N/_index.yaml` | Machine-readable index of a stage's prompts. |
| `reviews/stage-N.review.{md,yaml}` | Output of a stage-gate review: learnings, plan revisions, and the list of next-stage prompts generated. |
| `reviews/_TEMPLATE.review.{md,yaml}` | Templates a review gate fills in. |
| `schema/*.json` | JSON Schemas making every artefact validatable/parseable. |
| `artefacts/` | Created at runtime: deliverables produced by tasks (inventories, reports, harness output). |

## The loop (one sentence)

An orchestrator dispatches every task whose `deps` are all `done`; when a stage's tasks
are all `done`, the stage-gate **review task** (`R<n>`) runs, writes
`reviews/stage-<n>.review.*`, **revises `tasks.yaml` for downstream stages based on what
was learned**, and **emits `prompts/stage-<n+1>/*.md`** — which unblocks the next stage.

## Agent archetypes & model tiers

Model families (current best model in each tier at dispatch time):

| Archetype | Model | Scope | Used for |
|---|---|---|---|
| Scout | haiku→sonnet | read-only | inventories, broad code mapping |
| Mechanic | sonnet (haiku if trivial) | edit, batchable | well-specified mechanical changes |
| Implementer | sonnet | edit + build | new code from a clear spec |
| Infra | sonnet | CI / build files | harness, gates, pipelines |
| Architect | opus | read + design | decomposition, specs, ADRs |
| Diagnostician | opus | edit + instrumentation | root-cause nondeterminism |
| Reviewer | opus | read + run | correctness / GC-safety / perf review |

Effort: `low` (mechanical, one-shot) · `medium` (multi-file/judgement, 1–2 iterations) ·
`high` (novel design/subtle reasoning) · `max` (research-grade, high uncertainty).

## Validation loops (the throughput constraint)

Each task declares a `validation` loop — `local`, `ci`, or `corpus`. CI/corpus tasks
incur a multi-minute remote round-trip (the dominant cost observed during the
LLVM-backend work). Orchestrators should keep `local`-validatable work in flight while
`ci`/`corpus` tasks are queued, and never block an `opus` Diagnostician on a CI queue it
could pre-empt with local reasoning.

## Status values

`ready` (deps met, dispatchable) · `blocked` (deps unmet) · `in_progress` · `done` ·
`revised` (changed by a review gate; re-read before dispatch) · `dropped`.

## Conventions

- Task ids are stable (`S<stage>.<n>`, review gates `R<stage>`). Never renumber; mark
  `dropped` instead.
- Every task has a single owner, a single deliverable set (`produces`), and a checkable
  `done_when`.
- Every task prompt ends with a **Handback** block: the structured result the review
  gate consumes. Handbacks are how learning flows back into the plan.
