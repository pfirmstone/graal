# S0.5 — Test-app corpus

## Context (cold start)

The harness (S0.3) needs more than HelloWorld. Reproducibility bugs scale with the reachable
set: a trivial app barely exercises the analysis wobble, a large one exposes it broadly (the
investigation saw 9080 compiled functions from a "HelloWorld" that pulled in ~37k methods).
A tiered corpus lets the metric (S0.6) and the review gates see both presence and magnitude.

## Objective

A small, self-contained, dependency-light set of apps the harness can build twice, tiered
by size/feature coverage.

## Suggested tiers (adjust to what builds cleanly)

1. **tiny** — HelloWorld (baseline; already used).
2. **small** — exercises `instanceof`/`checkcast` across a class hierarchy and reflection on
   a handful of types (drives type-id assignment).
3. **small-fields** — many classes with many fields (drives field-offset layout).
4. **medium** — a console app using collections, streams, `java.time`, and a few service
   loaders (drives broader reachability).
5. **medium-concurrent** — spawns threads / parallel streams during init (more analysis
   surface; helps S3.2 separate parallelism-induced wobble).

Keep each app to a single directory with a `main`, buildable by the harness with no external
deps. Prefer pure-Java; avoid network/file I/O that would itself add nondeterminism to the
*program* (we want to test the *builder's* determinism, not the app's).

## Steps

1. Read the ADR for how the harness selects/builds an app (`--app NAME`).
2. Create each app under `determinism-corpus/<name>/`.
3. Register them with the harness selector.
4. Write `corpus-manifest.md`: per app — size class, lines, which determinism dimension it
   targets (type-ids / field-offsets / reachability breadth / parallelism).

## Definition of done

- >=5 apps, each builds twice via the harness on CI without app-side nondeterminism.
- Manifest maps each app to the dimension(s) it exercises.
