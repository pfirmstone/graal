# S0.6 — Reproducibility metric & trend

## Context (cold start)

The program needs a single number per app to know whether it is improving, and a
per-category breakdown to know *what* is left. This is the scoreboard the review gates read
to decide priorities and to prove progress.

## Objective

Extend the harness to compute and persist, per corpus app:

- **% bytes reproducible** — fraction of compared bytes identical across the two builds
  (across the captured stage artefacts).
- **% units reproducible** — fraction of comparable units (functions / object sections /
  files) byte-identical.
- **category breakdown** — count of divergences per S0.4 category (`id-renumber`,
  `offset-shift`, `path`, `timestamp`, `order`, `address`, `other`).

## Steps

1. Consume the diff + classifier outputs (do not re-diff).
2. Compute the metrics; write a machine-readable line per app (e.g. JSON in
   `metric.md`/a sibling `.json`) so a later dashboard or `git`-tracked history can trend it.
3. Print a compact human table at the end of the CI job.
4. Snapshot the baseline now (pre-fix) — this is the number stages 1–5 must move.

## Constraints / gotchas

- Keep the metric stable in definition (don't let it silently change meaning between runs,
  or trends become meaningless). Document the exact definition in `metric.md`.
- Exclude the known-cosmetic `; ModuleID` llvm-dis artefact and any path/timestamp bytes that
  Stage 1 will normalize, OR report them as their own category so improvement is visible.

## Definition of done

- CI prints the per-app table and persists a machine-readable snapshot.
- `metric.md` states the exact metric definitions and the baseline values.
