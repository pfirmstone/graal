# S0.2 — Design the whole-image build-twice-and-diff harness

## Context (cold start)

The program needs one harness that builds a corpus app **twice** and diffs the result,
attributing each divergence to a pipeline stage. A working prototype already exists for the
LLVM backend only: `mx llvm-backend-determinism-test` in
`substratevm/mx.substratevm/mx_substratevm.py` (functions `llvm_backend_determinism_test`,
`_hashes_under`, `_diff_hashes`, `_classify_stage`, `_dump_ir_diffs`,
`_default_backend_determinism_test`, `_objdump_diff`). Read it — your design generalizes it.

The Native Image pipeline: `inputs → points-to analysis → universe build →
heap/type/field layout → compile → link → image`. The harness must capture comparable
artefacts at as many of these boundaries as feasible, for **both** backends (LLVM and
ordinary), defaulting to the ordinary backend (it builds on all platforms; the LLVM
backend does not build on Windows).

## Objective

A short, decisive ADR (Architecture Decision Record) that the S0.3/S0.4/S0.7a tasks
implement without further design.

## Decisions the ADR must fix

1. **Stage boundaries captured.** Which artefacts are hashed/diffed at which boundary
   (e.g. final binary; object file pre-link; per-function code where available; and — via
   S0.7 — the serialized analysis result and universe). Note which are feasible now vs
   blocked on checkpoint/replay (S0.7).
2. **Backend abstraction.** One command, `--backend {default,llvm}`, sharing the diff +
   classifier; what each backend exposes for comparison.
3. **Artefact layout & determinism of the harness itself.** Where run-a/run-b artefacts and
   hashes land; the harness must not itself introduce nondeterminism (e.g. sort file lists).
4. **Interfaces for the classifier (S0.4)** and the **metric (S0.6)** — what data structure
   the diff produces so those tasks consume it cleanly.
5. **CI shape.** How it runs in `.github/workflows/native-image-determinism.yml`
   (gating vs informational steps; artefact upload), reusing the patterns in the existing
   `llvm-backend-determinism.yml`.

## Constraints / gotchas (carry into the ADR)

- The LLVM backend cannot be built on Windows (no JavaCPP win binary); design the default
  backend as the primary path.
- Every CI run is a multi-minute round-trip; the harness should produce maximal diagnostic
  signal per run (don't make developers iterate to learn the same thing twice).
- Keep `mx llvm-backend-determinism-test` working (it is a landed regression guard); prefer
  refactoring shared helpers over breaking it.

## Definition of done

- `adr-harness.md` records each decision above with a rationale and the rejected
  alternatives.
- An explicit list of stage boundaries the harness will capture in S0.3, and which are
  deferred to S0.7.
